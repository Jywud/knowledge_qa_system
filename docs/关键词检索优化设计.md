# 关键词检索优化设计（BM25 → PostgreSQL 全文检索）

## 背景

当前 BM25 每次提问把知识库全部 chunk 读进内存重建索引（`retrieval_service.hybrid_search` 无 limit 查询），数据量增长后每次问答都是一次全表加载 + 重新分词，响应时间随规模线性恶化。

## 候选方案对比

| 方案 | 说明 | 优点 | 代价 |
| --- | --- | --- | --- |
| A. 内存缓存 BM25 | 按 kb_id 缓存 BM25Retriever，文件变更时失效 | 改动小（约 50 行），无新依赖 | 仍需全量分词一次；多实例部署各存一份 |
| B. PG 全文检索（tsvector + GIN） | 中文分词用 zhparser 或 pg_jieba 扩展，与 pgvector 同库 | 查询性能与规模解耦；架构统一；删除/更新随事务一致 | 官方 pgvector 镜像不含中文分词扩展，需自建 Dockerfile 编译 zhparser + SCWS |
| C. 外置搜索引擎（Elasticsearch 等） | 新增独立服务 | 能力最强 | 运维成本大幅上升，当前规模不划算 |

## 当前状态与演进建议

当前实现已经使用 LangChain `BM25Retriever`，并且向量服务异常时会降级为纯 BM25。这解决了“向量通道不可用”的问题，但关键词通道仍是每次查询重建内存索引，数据量增长后会成为瓶颈。

## 推荐：分两步走

1. **短期（本次实施候选）**：方案 A 内存缓存，立刻消除"每次问答全表重建"的问题，风险最低。
2. **中期（数据量过万 chunk 后）**：切换方案 B，自建 `backend/docker/Dockerfile.pgvector`（基于 pgvector/pgvector:pg16 编译 zhparser），检索 SQL 换 `to_tsvector('chinese', content) @@ plainto_tsquery('chinese', :query)`，接口不变。

## 方案 A 实施要点

1. `retrieval_service` 增加模块级缓存 `{kb_id: (retriever, signature)}`。
2. signature = 该知识库 chunk 数量 + 最新 chunk 更新时间（或文件版本），变化即重建。
3. 文件上传/更新/删除成功后主动失效对应 kb 缓存。
4. 全局 fallback（kb_id 为空）不缓存。

## 方案 B 前置条件

1. 自建 PG 镜像并验证 zhparser 中文分词效果。
2. chunks 表增加 `content_tsv` 生成列 + GIN 索引（迁移脚本）。
3. docker-compose 换镜像，存量卷兼容性验证。

## 验证方式

方案 A：上传文件后提问命中正常；删除文件后提问不再命中（缓存已失效）。
方案 B：中文分词切分抽查 + 检索回归用例（`RUN_RETRIEVAL_TESTS=1`）全部通过。
