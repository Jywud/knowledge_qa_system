# 企业智能知识库系统 · 二阶段需求分析

版本：v1.0（2026-11-04）  
状态：待评审  
关联文档：[二阶段 PRD](./二阶段PRD.md) · [二阶段迭代计划](./二阶段迭代计划.md)

## 0. 结论先行

二阶段不建议先堆“多智能体”概念，而应先把系统从“能用的 Demo”推到“企业内部敢用的产品”。优先级建议如下：

1. **可信**：知识库权限、引用可追溯、文档版本不串、审计可查。
2. **可靠**：上传/解析/向量化可恢复、可重试、可看进度，更新失败不毁旧数据。
3. **好用**：停止生成、重新生成、反馈、会话搜索、错误提示、移动端可用。
4. **智能**：查询改写、Rerank、元数据过滤、知识缺口雷达，再考虑 Agentic RAG。

建议二阶段总周期 **10 周左右**（1 名全栈 + 兼职测试）；若配 1 名后端 + 1 名前端，可压缩到 **6-7 周**。前 6 周只做 P0 稳定化、权限、入库可靠性与引用，避免在不可靠的地基上继续加功能。

本次代码审计发现 **7 个 P0 级、13 个 P1 级实际问题**，详见第 7 节。最需要先处理的是：

- 删除知识库/用户可能因外键约束直接 500。
- 文件更新先删旧分块，新文件解析失败会留下空文件。
- 历史消息接口在知识库为空时返回 400，导致旧会话打不开。
- 流式问答使用原生 `fetch`，401/400 时前端显示空白回答。
- 管理员重置密码没有长度校验，可设置 1 位密码。

## 1. 现状盘点

### 1.1 已具备能力

| 模块 | 当前实现 | 评价 |
|---|---|---|
| 登录与用户 | JWT、admin/user 两种角色、管理员新增用户、个人改密、登录失败锁定 | 可用，但密码策略、审计、SSO 不足 |
| 知识库 | 多知识库、共享访问、管理员创建/编辑/删除 | 缺少成员/部门/文档级权限 |
| 文件管理 | md/txt/docx/pdf 上传、更新、删除、分块查看 | 有后台处理，但无进度、重试、版本回滚 |
| 文档解析 | PDF 表格转 Markdown、DOCX 按标题分组、表格按行聚合 | 已覆盖常见格式，扫描件/OCR 未覆盖 |
| 检索 | pgvector HNSW + BM25 + RRF 融合 | 方向正确，但 BM25 全表加载，无 Rerank |
| 问答 | LangGraph + SSE 流式、系统提示词、来源编号 | 可用，但缺少停止/重试/反馈/错误态 |
| 记忆 | Postgres Checkpoint + 最近 20 条 + 增量摘要 | 已可用，但触发参数存在“配置不生效”问题 |
| 审计 | `audit_logs` 表，记录文件/用户/知识库操作 | 只有落库，没有查询页面和登录审计 |
| 测试 | 21 个测试通过，2 个检索回归用例默认跳过 | 核心链路有基础，但覆盖仍偏薄 |

### 1.2 当前产品定位

当前更像“企业内部知识库问答工具”，还不是“企业知识平台”。差距主要不在模型，而在：

- 谁可以看哪个知识库、哪份文档。
- 文档更新后，历史回答的引用是否仍然可信。
- 上传 100 份文档后，管理员是否能知道哪些成功、哪些失败、哪些内容缺失。
- 出问题时，能否定位是检索没召回、模型没回答，还是文档本身没有写。

## 2. 外部对标与趋势

### 2.1 同类产品的基础能力

参考 RAGFlow、Dify、FastGPT 等产品的公开能力，企业知识库的“标配”已经比较明确：

| 能力 | 说明 | 本项目现状 |
|---|---|---|
| 多格式解析 | PDF/DOCX/Markdown/TXT/HTML/Excel，表格与图片处理 | 已有前四种，缺 OCR/Excel/HTML |
| 分块可视化 | 查看、编辑、重建分块 | 可查看，不能编辑/重建 |
| 混合检索 | 向量 + 关键词 + Rerank | 已有前两项，缺 Rerank |
| 引用溯源 | 文件名、页码、片段、原文定位 | 有来源弹窗，但引用会随文件更新失效 |
| 知识库隔离 | 空间/成员/权限 | 只有共享库，无成员权限 |
| 应用编排 | 工作流、Agent、工具调用 | 只有固定 RAG 图 |
| 运营能力 | 命中率、未回答问题、反馈 | 基本没有 |

参考：

- [RAGFlow 文档](https://ragflow.io/docs/dev/)
- [Dify 知识库文档](https://docs.dify.ai/en/guides/knowledge-base/readme)
- [FastGPT 介绍](https://doc.fastgpt.io/en/guide/introduction)

### 2.2 2026 年值得关注的方向

1. **权限感知检索（Permission-aware RAG）**  
   权限过滤必须发生在检索之前，而不是把无权内容塞进 Prompt 再让模型“不要说”。Oracle 的 2026 年文章明确把“检索前 ACL 过滤”列为企业 RAG 的关键设计。  
   [Oracle：Build a permission-aware RAG application](https://blogs.oracle.com/developers/build-a-permission-aware-rag-application)

2. **Agentic Retrieval / 查询规划**  
   Azure AI Search 的 agentic retrieval 把复杂问题拆成多个子查询，再合并结果。适合“对比两份制度”“先查 A 再查 B”这类多跳问题，但不适合作为第一优先级。  
   [Microsoft：Agentic retrieval](https://learn.microsoft.com/en-us/azure/search/search-agentic-retrieval-concept)

3. **GraphRAG / 关系型知识**  
   Microsoft GraphRAG 通过实体和关系图回答“全局性、跨文档”的问题。亮点强，但构建成本高，建议先做小范围试点，不要全量替换现有 RAG。  
   [Microsoft GraphRAG](https://microsoft.github.io/graphrag/) · [论文](https://arxiv.org/abs/2404.16130)

4. **RAG 评估与可观测性**  
   RAGAS、TruLens 等工具把“回答好不好”拆成上下文召回、上下文精度、忠实度、答案相关性等指标。企业落地不能只看“感觉答得不错”。  
   [RAGAS 文档](https://docs.ragas.io/) · [TruLens RAG Triad](https://www.trulens.org/getting_started/core_concepts/rag_triad/)

5. **知识缺口与内容运营**  
   把“未回答/低分/用户点踩”的问题聚类，反推缺哪份文档、哪段内容过期。这是比“再加一个 Agent”更能提升实际命中率的功能。

6. **连接器与开放能力**  
   企业知识散落在飞书/钉钉/Confluence/SharePoint/网盘。能否定时同步、增量更新、映射权限，决定了系统能不能真正成为“企业知识入口”。

7. **多模态与表格理解**  
   扫描 PDF、图片、复杂表格仍然是企业文档的大头。OCR、版面分析、表格结构化是二阶段后期或三阶段的重点。

### 2.3 不建议现在投入的方向

- 全量 GraphRAG：构建和维护成本高，当前数据规模与问题类型未必需要。
- 复杂可视化工作流编排：会显著增加前端和后端复杂度，先把固定 RAG 链路做稳。
- 完全自治的多智能体：缺少评估集时，无法判断多 Agent 是否真的更好。
- 自研向量数据库/检索引擎：pgvector 在中小规模企业知识库足够，继续用好 PostgreSQL 即可。

## 3. 目标用户与核心场景

| 角色 | 核心诉求 | 二阶段要解决的问题 |
|---|---|---|
| 普通员工 | 快速问、答案可信、能看原文 | 权限内问答、引用可点、历史可查、反馈 |
| 知识库管理员 | 上传后知道是否成功、内容是否过期 | 进度、失败重试、版本回滚、健康度 |
| 部门负责人 | 本部门知识不被越权访问 | 知识库成员/部门权限 |
| IT/安全 | 可审计、可限制、可运维 | 审计页面、密码策略、限流、健康检查 |
| 管理者 | 知道系统用得怎么样、缺什么 | 使用分析、知识缺口雷达 |

核心场景：

1. 新员工问“报销标准是什么”，得到答案并能打开制度原文。
2. 管理员上传 20 份制度，能看到每份的解析进度和失败原因。
3. 制度更新后，历史回答明确标记“引用的是旧版本”，不误导用户。
4. 员工问了一个知识库没有的问题，系统明确说“不知道”，并进入知识缺口列表。
5. 部门知识库只允许本部门访问，检索结果不会越权。

- 检索调试台。
- 会话重命名/置顶/搜索/导出。

### 5.3 P2：生态与亮点（第 10 周或缓冲期，可选）

- 飞书/钉钉/Confluence/SharePoint 连接器（选 1 个先做）。
- OpenAI 兼容 API、MCP Server、嵌入式问答组件。
- Agentic RAG 小范围试点。
- GraphRAG/OCR 技术验证，不承诺上线。

### 5.4 明确不做

- 普通用户自建知识库（保持管理员创建）。
- 多租户计费、复杂组织架构同步。
- 全量移动端 App。
- 完全替代现有 OA/IM 的工作流引擎。

## 6. 关键产品设计

### 6.1 权限模型

二阶段建议做“够用的权限”，不要一上来做文档级 ACL。

```
users(id, username, role[admin|user], department)
knowledge_bases(id, name, visibility[public|department|private], owner_id)
kb_members(id, kb_id, user_id, permission[viewer|editor|owner])
kb_departments(id, kb_id, department)
```

规则：

- `admin`：全部知识库可见，可管理用户与所有知识库。
- `owner/editor`：可上传、更新、删除该库文件。
- `viewer`：可问答、查看文件与分块。
- `public`：所有登录用户可见。
- `department`：仅指定部门可见。
- `private`：仅成员可见。

检索 SQL 必须先算出 `allowed_kb_ids`，再拼到向量检索和 BM25 查询里；禁止“先检索全部，再在 Prompt 里要求模型保密”。

### 6.2 入库任务与版本

建议新增：

```
ingestion_jobs(id, file_id, file_version, stage, progress, attempts,
               status[queued|parsing|chunking|embedding|ready|failed|canceled],
               error_message, created_at, started_at, finished_at)
file_versions(id, file_id, version, storage_path, checksum, size,
              status[processing|ready|failed], created_at)
chunks(id, file_id, version_id, chunk_index, page_no, heading_path,
       content, token_count, embedding)
```

更新流程：

1. 保存新文件到新路径，计算 SHA-256。
2. 创建新 `file_version`，状态 `processing`。
3. 解析、分块、向量化到新版本。
4. 全部成功后，事务内把 `files.active_version` 指向新版本。
5. 失败时保留旧版本，新版本标记 `failed`，旧版本继续可检索。
6. 旧版本至少保留 7 天或最近 2 个版本，便于回滚和引用追溯。

### 6.3 引用与原文定位

`messages.sources` 不再只存文件名和 `chunk_index`，建议存：

```json
{
  "chunk_id": 123,
  "file_id": 45,
  "file_version": 3,
  "filename": "员工手册.docx",
  "page": 12,
  "heading_path": "第三章 > 报销制度",
  "score": 0.82,
  "excerpt": "……",
  "status": "active"
}
```

前端点击来源时调用 `GET /api/chunks/{chunk_id}`，不要拉整个文件的全部分块。文件已删除或版本已过期时，显示“该引用来自旧版本/文档已删除”，不要默默展示新内容。

### 6.4 检索增强

建议顺序：

1. **查询改写**：多轮追问时，把“那它呢”改写成完整问题；用小模型，超时降级为原问题。
2. **混合召回**：向量 Top 20 + 关键词 Top 20。
3. **Rerank**：用 `bge-reranker-v2-m3` 或企业已有重排服务，取 Top 5。
4. **父块扩展**：命中子块后，取所在章节/父块作为上下文。
5. **阈值与兜底**：低分时明确“不知道”；向量服务异常时降级 BM25；向量为空但关键词强命中时允许 BM25 兜底（可配置）。

注意：Ollama 主要跑生成/嵌入，Rerank 模型通常需要 TEI、Xinference、Infinity 或云服务，不要假设 Ollama 直接支持。

### 6.5 知识缺口雷达

数据来源：

- 模型回答“知识库中没有相关内容”。
- 检索最高分低于阈值。
- 用户点踩并选择“答非所问/内容缺失/内容过期”。
- 同一问题被多个用户反复提问。

处理流程：

1. 对问题做向量聚类。
2. 生成缺口主题和示例问题。
3. 管理员标记“需补充文档/需更新文档/无需处理”。
4. 补充文档后，系统回放这些问题，验证是否已命中。

这是二阶段最容易做出“业务价值感”的亮点功能。

### 6.6 评估与可观测性

建议建立最小评估集：

- 每个知识库 30-50 个问题，标注期望来源文件/章节。
- 离线指标：Hit@5、MRR、上下文精度、引用准确率、无答案准确率。
- 在线指标：首 token 延迟、P95 总耗时、点踩率、无答案率、每日 token 成本。
- 每次检索记录：query、改写后 query、各路召回 ID/分数、最终上下文、模型、耗时。

工具可以从轻量开始：先用脚本 + PostgreSQL 记录，后续再接 Langfuse/OpenTelemetry。不要一开始就上复杂平台。

## 9. 风险与待确认

1. **权限模型复杂度**：部门数据从哪来？是否有统一组织架构/HR 系统？二阶段先手工维护部门，还是接 LDAP？
2. **文档版本保留策略**：保留最近 2 个版本还是固定 30 天？涉及磁盘成本与引用追溯。
3. **Rerank 部署方式**：本地 TEI/Xinference，还是云服务？需要确认服务器 GPU/内存。
4. **全文检索扩展**：PostgreSQL 是否允许安装 `pg_jieba`/`zhparser`？如果不行，先做按库缓存 BM25。
5. **连接器优先级**：飞书、钉钉、Confluence、SharePoint 先接哪一个？取决于公司实际文档在哪。
6. **是否允许普通用户创建知识库**：当前明确不允许，二阶段保持；后续可作为权限模型的扩展。
