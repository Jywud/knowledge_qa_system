# 异步向量化设计

## 背景

当前文件上传接口同步完成解析、切分、嵌入向量化和落库。大 PDF 解析慢、逐块调用 Ollama 嵌入耗时，导致上传请求长时间挂起，前端可能超时。`files.status` 字段已存在但未真正使用。

## 目标

1. 上传接口立即返回，向量化在后台执行。
2. 前端可感知处理进度：文件列表显示处理中状态。
3. 处理失败时状态可见，不产生"假 ready"数据。
4. 支持一次选择多个文件上传，每个文件独立处理、独立展示状态。

## 多文件上传

- 前端 `el-upload` 开启 `multiple`，一次可选择多个文件（逐个加入请求）。
- 后端为每个文件独立执行"保存 → 后台向量化"流程，互不影响：某个文件失败不影响其他文件。
- 文件列表按状态独立展示，用户可同时看到多个"处理中"。
- 失败的文件可单独重新上传。

## 方案

### 状态流转

```
uploaded（已保存文件，向量未生成）
   → processing（后台任务解析+向量化中）
   → ready（完成）
   → failed（失败，原因记录在 status_message）
```

`files` 表新增 `status_message` 列（失败原因），通过 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 平滑升级。

### 后端流程

1. 上传接口：保存文件 + 创建 FileRecord（status=processing）+ 返回响应，耗时毫秒级。
2. 使用 FastAPI `BackgroundTasks` 在响应返回后执行 `ingest_file`：
   - 成功：status=ready
   - 异常：status=failed，status_message=异常摘要，并清理已产生的半成品 chunk
3. 文件更新（重新上传）复用同一机制。

### 前端流程

1. 上传成功后提示"文件已上传，正在后台解析"，文件列表立即出现（状态=处理中）。
2. 文件列表存在 processing/failed 状态时每 3 秒轮询 `/api/files?kb_id=`，全部 ready/failed 后停止。
3. 状态列展示标签：处理中（warning）/ 就绪（success）/ 失败（danger，悬浮显示原因）。

### 约束

1. 处理中的文件不可被删除/更新（接口返回 409），避免与后台任务竞争。
2. 服务重启时遗留的 processing 状态文件：启动时统一标记为 failed（提示重新上传），不做断点续传。

## 改动范围

| 文件 | 改动 |
| --- | --- |
| `backend/app/models.py` | FileRecord 增加 status_message |
| `backend/app/main.py` | 启动时补列 + 重置遗留 processing |
| `backend/app/routers/files.py` | 上传/更新改用 BackgroundTasks，状态校验 |
| `backend/app/services/document_service.py` | ingest 包装为带状态回写的后台函数 |
| `frontend/src/views/FileManager.vue` | 状态列 + 轮询 |
| `frontend/src/views/FileManager.vue` | 上传组件开启多选 |

## 验证方式

1. 上传大 PDF，接口应秒级返回，列表显示"处理中"，完成后变"就绪"。
2. 停掉 Ollama 上传文件 → 状态"失败"，悬浮可见原因。
3. 处理中删除文件 → 返回 409。
