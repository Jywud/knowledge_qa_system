# 角色权限初始化与旧知识库保留

本轮按全新系统使用，不继承旧共享权限。保留知识库、文件记录、分块（含向量）、原始上传文件，以及为创建人/上传人外键保留的用户行。用户密码不会改变。原 `users.role` 列仅在第一次初始化时用于识别旧管理员，随后在同一事务内删除，避免旧列的 `NOT NULL` 约束阻塞新系统创建用户。

第一次执行会创建 `roles`、`user_roles`、`role_knowledge_bases`、`schema_migrations`，创建系统键为 `system_admin` 的“系统管理员”角色，并将旧 `role=admin` 的账号关联到该角色。普通账号无角色、无知识库授权，须管理员重新分配。不会创建旧共享访问角色，不会自动给新知识库授权。若不存在管理员，则整个事务失败并回滚。

首次迁移在同一事务内先清理旧 `messages`，再清理旧 `conversations`，不保留、不补绑旧会话，不让旧会话外键阻塞知识库删除。执行前会检查会话/消息的外键依赖，若存在已知消息链以外的依赖，则明确停止并回滚，避免误删业务数据。不会删除或修改知识库、文件、分块及向量，不访问原文件字节。

迁移为新会话增加记忆版本和可空的 `memory_thread_id VARCHAR(255)`，用于指向通过最终权限与记忆版本校验、并与助手回复一同提交的已完成状态。新会话使用独立的记忆边界，旧 Checkpoint 与未完成任务不能作为后续记忆来源。角色变更会递增记忆版本并清除此指针。

## 执行步骤

1. 停止旧后端，安排维护窗口，避免旧程序同时写入。
2. 备份数据库与 `backend/uploads/` 原始文件（若配置了其他上传目录，备份实际目录）。数据库备份须包括向量数据、用户和外键依赖；确认备份可恢复。
3. 在仓库根目录只读预检：

   ```powershell
   backend/.venv/Scripts/python.exe -B backend/scripts/migrate_roles.py --plan
   ```

   输出仅为按旧角色统计的用户数、知识库数、文件数、分块数和旧会话数。不输出账号、密钥、正文或向量。预检不要求新表/新列存在，不建表。

4. 核对计数和管理员，确认本次将清理全部旧会话和消息后，明确执行：

   ```powershell
   backend/.venv/Scripts/python.exe -B backend/scripts/migrate_roles.py --apply
   ```

5. 当前版本还需运行 `backend/scripts/migrate_chat_scope.py --plan` 和 `--apply`，增加跨库会话范围字段；该步骤不会清理角色系统下已有会话，详见[跨库问答说明](./跨库问答说明.md)。

6. 启动新后端，使用原管理员账号登录，为普通账号重新分配角色和知识库范围，验证知识库文件仍存在。

两种模式必须显式选择其一。脚本读取现有本地配置，不修改配置或密钥。PostgreSQL 使用事务级 advisory lock 串行初始化；SQLite 显式开启写事务，以确保 DDL 也可回滚。

迁移版本为 `roles_v1`。标记、结构、旧角色列删除、旧会话清理、管理员关联在同一事务提交。成功后重复执行不会重新授权已撤权的管理员，也不会删除新会话/消息，或重置记忆版本、已完成状态指针。旧库缺少标记时，新后端应明确拒绝启动，不在启动时自动迁移。全新安装由启动流程在同一事务中建立用户、系统管理员角色、关联和初始标记，无须运行旧库初始化脚本。

## 验证与失败处理

隔离 SQLite 测试覆盖只读预检、知识库/文件/分块及向量指纹和原始文件字节不变、仅旧管理员映射、普通账号零授权、旧 `NOT NULL` 角色列移除后新 ORM 用户写入成功、旧会话不再阻塞知识库删除、未知外键依赖明确拒绝、重复执行不重授且保留新会话，以及 DDL/seed/标记写入故障的整体回滚：

```powershell
cd backend
.venv/Scripts/python.exe -B -m pytest tests/test_role_migration.py -q
```

执行失败后保持维护窗口，检查管理员与数据库结构，修复原因后重新执行。不要手动伪造或删除迁移标记。恢复时使用迁移前数据库与上传文件备份，并核对知识库、文件、分块计数。不要将旧版本后端直接连到新系统数据库；旧版本的共享权限模型不符合本轮角色隔离要求。本次已在本地开发数据库执行初始化并完成保留数据核验，未操作生产环境；具体结果见[角色权限验收记录](./角色权限验收记录.md)。
