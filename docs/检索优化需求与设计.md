# 检索优化需求与设计

版本：v1.0（2026-10-26）  
范围：本次先实现「混合检索」和「知识块元数据增强」，rerank 与多轮查询改写后续再做。

## 1. 背景与问题

当前问答检索只有 Chroma 向量检索：

1. 对精确关键词、型号、编号、文件名类问题不够稳。
2. 向量结果可能有语义相近但内容重复的分块。
3. 来源只展示文件名和页码，缺少文件类型、知识库名称、上传时间等辅助信息。

## 2. 需求

### 2.1 混合检索

问答时同时使用两种召回方式：

| 检索方式 | 数据源 | 目标 |
|---|---|---|
| 向量检索 | Chroma | 找语义相近内容 |
| BM25 关键词检索 | PostgreSQL `chunks` 表 | 找精确词、编号、型号、专有名词 |

要求：

1. 仍按当前会话绑定的 `kb_id` 限定检索范围。
2. 两种检索各自取一部分候选，使用 RRF 融合排序，最终返回系统设置里的 `TopK`。
3. 同一个分块在两种结果中出现时只保留一个。
4. 使用 LangChain Community 的 `BM25Retriever`，底层依赖 `rank_bm25`。
5. 现有 `TopK` 含义保持不变：最终给大模型的知识块数量。

### 2.2 分块元数据增强

检索结果和问答来源补充以下元数据：

| 字段 | 来源 | 说明 |
|---|---|---|
| `source` | `files.filename` | 文件名 |
| `page` | `chunks.page_no` | 页码，普通文档可为 0 |
| `file_type` | `files.file_type` | 文件类型，如 `md` / `pdf` |
| `kb_name` | `knowledge_bases.name` | 所属知识库名称 |
| `uploaded_at` | `files.created_at` | 文件上传时间 |
| `file_id` / `chunk_index` | 现有元数据 | 用于去重和溯源 |

前端来源标签补充展示：文件类型、知识库名称、页码。上传时间不直接挤进标签，避免 UI 过重。

## 3. 技术设计

### 3.1 候选召回

每个检索通道先召回：

```text
candidate_k = max(TopK * 2, 10)
```

向量通道继续使用 Chroma `similarity_search`，关键词通道从 PostgreSQL 读取当前知识库的分块并计算 BM25 分数。

### 3.2 BM25 分词

为了避免中文分词依赖，使用轻量规则：

1. 英文、数字、下划线按连续字符串切分。
2. 中文字符按单字切分。
3. 统一转小写。
4. 去掉标点符号。

这样不引入 jieba 等新依赖，也能覆盖常见编号、型号和中文关键词。  
BM25 打分由 LangChain Community 的 `BM25Retriever` 完成，实际底层实现是 `rank_bm25.BM25Okapi`。

### 3.3 RRF 融合

两个通道的候选按排名参与 RRF：

```text
score = Σ 1 / (60 + rank)
```

按融合分数倒序取 `TopK`。

### 3.4 元数据补全

关键词结果天然来自 PostgreSQL，可一次联查 `files` 和 `knowledge_bases` 拿到完整元数据。  
向量结果返回后，用 `file_id + chunk_index` 回查内存中的分块索引表，补全 `file_type`、`kb_name`、`uploaded_at`。

### 3.5 兼容性

1. 旧向量里已有 `source`、`page`、`kb_id`、`file_id`、`chunk_index`，不需要重建向量。
2. 新上传文件继续写入相同向量 ID 规则。
3. 删除文件时仍然按现有逻辑删除分块和向量。

## 4. 验收要点

1. 相同问题仍能返回语义相关内容。
2. 精确关键词、编号、型号更容易被召回。
3. 多知识库场景下不会跨 `kb_id` 检索。
4. 回答来源能显示文件类型和知识库名称。
5. 新增依赖仅为 `rank_bm25`；检索链路使用 LangChain Community 的 `BM25Retriever`。
6. 删除文件后，其分块不再参与关键词检索。
