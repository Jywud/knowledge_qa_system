# 企业智能知识库系统 · 二阶段迭代计划

版本：v1.1（2026-11-11）  
状态：M0 部分实施，后续阶段待评审  
关联文档：[二阶段需求分析](./二阶段需求分析.md) · [二阶段 PRD](./二阶段PRD.md)

## 1. 计划假设

- 默认投入：1 名全栈开发（5 人日/周）+ 0.5 名测试。
- 若增加 1 名后端或前端，可并行压缩到 6-7 周。
- 不包含采购、等保、SSO 对接等外部流程时间。
- 估算是“可交付 + 有测试 + 有文档”的工程量，不是纯编码时间。

## 2. 总体节奏

| 阶段 | 周期 | 目标 | 退出条件 |
|---|---|---|---|
| M0 稳定化 | 第 1 周 | 修复会阻断使用的 P0 缺陷 | 现有测试 + 新增回归通过 |
| M1 权限 | 第 2-3 周 | 知识库权限与检索前过滤 | 越权用例全部通过 |
| M2 入库可靠性 | 第 3-4 周 | 任务化、可重试、版本化更新 | 更新失败不丢旧版本 |
| M3 引用与对话 | 第 5 周 | 引用稳定、停止/重试/反馈 | 历史引用可追溯 |
| M4 安全与评估 | 第 5-6 周 | 审计、限流、密码策略、评估集 | P0 验收通过，可内部试运行 |
| M5 检索增强 | 第 7-8 周 | 改写、Rerank、PG 全文检索 | 评估集指标达标 |
| M6 知识运营 | 第 9 周 | 缺口雷达、调试台、看板 | 管理员可闭环运营 |
| M7 缓冲/可选 | 第 10 周 | 连接器、开放 API、Agentic 试点 | 按剩余时间取舍 |

P0 建议在第 6 周末冻结并试运行；P1 在第 9 周末交付；第 10 周只做缓冲和可选能力，不再塞 P0。

**关键决策**

- 二阶段先手工维护部门，不接 LDAP。
- `public` 为默认值，保证升级后现有用户仍可访问。
- 会话绑定 KB 后，权限被回收时历史可读、不可继续问答。

| ID | 任务 | 类型 | 估算 | 依赖 | 验收 |

**实现建议**

- 先用数据库任务表 + 单进程 worker，避免新增 Redis。
- worker 用 `SELECT ... FOR UPDATE SKIP LOCKED` 取任务，天然支持未来多实例。
- 解析、分块、Embedding 分阶段更新 `progress`，不要只显示“处理中”。
- 旧版本保留策略先做“最近 2 个版本 + 30 天”，做成配置。

## 4. 关键路径与并行建议

关键路径：

```
M0 修复
  → M1 权限
  → M2 版本化入库
  → M3 引用稳定
  → M4 P0 验收
  → M5 检索增强
  → M6 知识运营
```

可并行：

- M1 前端权限页可与 M2 后端任务表并行。
- M3 对话体验（停止/反馈/会话管理）可与 M2 后半段并行。
- M4 评估集可与 M2/M3 并行准备。
- M5 的 Rerank 与 PG 全文检索可分别由两人并行。

不建议并行：

- 权限模型与引用版本同时改，容易在迁移上互相阻塞。
- M2 版本化未完成前，不要先做“引用旧版本提示”，否则数据结构会返工。

## 5. 测试计划

### 5.1 单元测试

- 权限：admin/owner/editor/viewer/无权限。
- 任务状态机：queued/parsing/chunking/embedding/ready/failed/canceled。
- 版本切换：成功切换、失败保留、回滚。
- 引用：同名文件、旧版本、已删除文件。
- 摘要：阈值、增量合并、失败降级。
- 限流：并发 1、每分钟 N 次、重启后仍生效。

### 5.2 集成测试

- 上传 → 解析 → 向量化 → 问答 → 引用打开。
- 更新失败 → 旧版本仍可问答。
- 撤权 → 检索不到、问答 403。
- 停止生成 → 部分回答落库。
- 删除知识库/用户 → 不 500，数据按规则处理。

### 5.3 手工验收

- 10 个文件批量上传，观察进度与失败重试。
- 100 条会话列表滚动与搜索。
- 移动端 375px 宽度问答。
- 断网/刷新/关闭页面后的生成恢复。
- Ollama/LLM 任一故障时的降级提示。

## 6. 发布计划

### 6.1 功能开关

| 开关 | 默认 | 说明 |
|---|---|---|
| `KB_ACL_ENABLED` | true | 关闭时退回全员共享，仅用于回滚 |
| `INGESTION_WORKER_ENABLED` | true | 关闭时上传后不自动处理 |
| `RERANK_ENABLED` | false | 先灰度一个知识库 |
| `QUERY_REWRITE_ENABLED` | true | 失败自动降级 |
| `GAP_RADAR_ENABLED` | false | 先观察数据质量 |

### 6.2 发布步骤

1. 备份数据库与 `uploads/`。
2. 在预发库执行迁移脚本，跑回归。
3. 生产低峰发布后端，再发布前端。
4. 验证 `/health/ready`、登录、上传、问答、引用。
5. 观察 24 小时：错误率、P95、入库失败率、无答案率。
6. 异常回滚：镜像回滚 + 执行对应回滚 SQL；功能开关先关。

### 6.3 回滚策略

- 代码：保留上一版镜像，5 分钟内可回滚。
- 数据：迁移只新增列/表，不删除旧列；回滚 SQL 先保留数据。
- 权限：`KB_ACL_ENABLED=false` 可临时退回共享模式，但需安全负责人确认。
- 任务：失败任务不自动删除，保留错误信息供排查。

## 7. 风险清单

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| 权限迁移导致旧用户看不到库 | 中 | 高 | 默认 public；迁移前统计各库访问量；灰度 |
| 版本化改造影响现有上传 | 中 | 高 | 先双写/兼容旧字段；保留旧路径 |
| Rerank 服务延迟高 | 中 | 中 | Top 20 限制、超时 1.5s、失败降级 |
| pg_jieba 无法安装 | 中 | 中 | 保留按库缓存 BM25 方案 |
| 任务 worker 与 Web 进程争资源 | 中 | 中 | 限制并发 1-2；大文件排队 |
| 旧引用数据不兼容 | 高 | 中 | 新旧格式兼容；缺字段降级展示 |
| 工期被 P2 功能挤占 | 高 | 高 | P0 冻结后不再加需求；P2 只做 1-2 项 |

## 8. 完成定义（DoD）

每个任务完成必须满足：

- 代码通过评审，遵循现有 router/service/schema 分层。
- 有对应测试，或说明无法自动化的原因和手工步骤。
- 有数据库迁移与回滚脚本（涉及数据变更时）。
- 有错误处理、日志、权限校验。
- 有用户可见的加载/空/错误状态。
- 更新相关文档和 `.env.example`（涉及配置时）。
- 在预发环境验证通过。
